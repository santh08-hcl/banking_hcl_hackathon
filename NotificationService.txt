# ✅ **2. Notification Service – API Design**

Although notifications are best triggered via **events (Kafka/RabbitMQ)** from Payment Service, the service still needs REST APIs for:

* External or manual notifications
* Debugging
* Retry triggers
* Querying notification history

---

# **API 1: Send Notification to Merchant (REST endpoint)**

**POST /api/v1/notification/merchant**

### **Purpose**

Payment Service calls this after merchant credit and ledger update.

### **Request Payload**

```json
{
  "transactionId": "TXN-99111",
  "merchantId": "M456",
  "amount": 2475.00,
  "currency": "INR",
  "message": "Payment successfully credited to your account"
}
```

### **Response**

```json
{
  "notificationId": "NOTIF-55781",
  "status": "DELIVERED"
}
```

---

# **API 2: Send Notification to Customer**

**POST /api/v1/notification/customer**

Used by Payment Service or Wallet Service.

### **Request**

```json
{
  "customerId": "C123",
  "transactionId": "TXN-99111",
  "status": "SUCCESS",
  "message": "Your payment of INR 2500 for Nike Shoes was successful."
}
```

### **Response**

```json
{
  "notificationId": "NOTIF-88321",
  "status": "DELIVERED"
}
```

# ✅ **3. Recommended Event-Based Integration**

Payment Service publishes:

```
EVENT: PAYMENT_SUCCESS
EVENT: PAYMENT_FAILED
```

Notification Service consumes:

```
Topic: payments.notifications
```

Example event payload:

```json
{
  "eventType": "PAYMENT_SUCCESS",
  "transactionId": "TXN-99111",
  "customerId": "C123",
  "merchantId": "M456",
  "amount": 2500,
  "currency": "INR",
  "productName": "Nike Shoes"
}
```

Notification Service then:

1. Sends merchant notification
2. Sends customer notification
3. Logs the event

# **A. notification table**

Stores every notification sent.

| Column          | Type                                             | Description           |
| --------------- | ------------------------------------------------ | --------------------- |
| notification_id | VARCHAR                                          | PK                    |
| transaction_id  | VARCHAR                                          | FK to payment service |
| customer_id     | VARCHAR                                          | nullable              |
| merchant_id     | VARCHAR                                          | nullable              |
| channel         | ENUM(EMAIL, SMS, PUSH)                           | delivery method       |
| status          | ENUM(PENDING, SENT, DELIVERED, FAILED, RETRYING) |                       |
| message         | TEXT                                             |                       |
| created_at      | TIMESTAMP                                        |                       |
| sent_at         | TIMESTAMP                                        |                       |
| delivered_at    | TIMESTAMP                                        |                       |

---

# **B. notification_retry_log**

Tracks retries by Notification Service.

| Column          | Type                  |
| --------------- | --------------------- |
| id              | BIGINT PK             |
| notification_id | VARCHAR               |
| retry_count     | INT                   |
| status          | ENUM(SUCCESS, FAILED) |
| timestamp       | TIMESTAMP             |

---

# **C. notification_event_log**

Stores raw events received from Payment Service.

Useful for:

* Debugging
* Replaying events
* Auditing

| Column         | Type       |
| -------------- | ---------- |
| event_id       | VARCHAR PK |
| event_type     | VARCHAR    |
| transaction_id | VARCHAR    |
| payload        | TEXT       |
| timestamp      | TIMESTAMP  |

---

# **D. communication_channel_config** (optional)

Defines templates per channel.

| Column        | Type    |
| ------------- | ------- |
| id            | BIGINT  |
| channel       | ENUM    |
| template_name | VARCHAR |
| template_body | TEXT    |

# 🧩 **6. End-to-End Notification Flow**

### **When payment succeeds**

1. Payment Service → publishes event
2. Notification Service consumes event
3. Creates 2 entries in `notification` table
4. Sends:

   * Merchant alert
   * Customer alert
5. Updates both records → DELIVERED
6. Logs event in `notification_event_log`
