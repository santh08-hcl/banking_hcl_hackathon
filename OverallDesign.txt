# ✅ **Positive Case 1: Customer buys a product successfully**

### **Actors:**

Customer → Wallet Service → Payment Service → Merchant Service → Notification Service

---

## **Step 1: Customer views wallet**

Customer opens the app.

**API Call**
`GET /wallet/C123`

**Result**

```
{
  "customerId": "C123",
  "balance": 5400,
  "currency": "INR"
}
```

---

## **Step 2: Customer initiates purchase**

Customer wants to buy *Nike Shoes* worth ₹2500.

**API Call**
`POST /wallet/initiatePurchase`

```json
{
  "customerId": "C123",
  "merchantId": "M456",
  "productName": "Nike Shoes",
  "productCost": 2500,
  "currency": "INR"
}
```

### **Wallet Service actions**

✔ Checks wallet exists
✔ Checks currency IN INR
✔ Checks balance >= 2500
✔ Creates transaction request (REQ-101)
✔ Calls Payment Service

---

## **Step 3: Wallet Service → Payment Service**

**API Call**
`POST /payment/execute`

```json
{
  "requestId": "REQ-101",
  "customerId": "C123",
  "walletId": "W123",
  "merchantId": "M456",
  "amount": 2500,
  "currency": "INR",
  "productName": "Nike Shoes"
}
```

---

## **Step 4: Payment Service processes payment**

Payment Service performs:

✔ Deduct wallet balance
✔ Calculate fee (₹25)
✔ Net amount to merchant = 2475
✔ Credit merchant account
✔ Write ledger
✔ Write audit
✔ Mark transaction SUCCESS

**Payment Service Response**

```json
{
  "transactionId": "TXN-5001",
  "status": "SUCCESS",
  "walletFee": 25,
  "netAmountCredited": 2475
}
```

---

## **Step 5: Payment Service → Merchant Service**

**API Call**
`POST /merchant/credit`

```json
{
  "transactionId": "TXN-5001",
  "merchantId": "M456",
  "amount": 2475,
  "currency": "INR"
}
```

Merchant service updates:

✔ Merchant balance increased
✔ Credit log stored
✔ Mark TXN-5001 as credited

**Response**

```json
{
  "transactionId": "TXN-5001",
  "status": "SUCCESS",
  "merchantBalance": 12475
}
```

---

## **Step 6: Payment Service → Notification Service**

Payment Service triggers both merchant & customer notifications.

### **Notify Merchant**

`POST /notification/merchant`

```json
{
  "transactionId": "TXN-5001",
  "merchantId": "M456",
  "message": "Payment of ₹2475 received."
}
```

### **Notify Customer**

`POST /notification/customer`

```json
{
  "transactionId": "TXN-5001",
  "customerId": "C123",
  "message": "Your payment of ₹2500 for Nike Shoes was successful!"
}
```

Notification Service marks them as **DELIVERED**.

---

## **Step 7: Wallet Service updates request**

Wallet Service updates request REQ-101 → SUCCESS.

**Customer sees:**
“Payment Successful — Transaction ID TXN-5001”

# 1) Wallet Service — tables & DDL

### `customer`

Stores customer master data.

```sql
CREATE TABLE customer (
  customer_id     VARCHAR(36) PRIMARY KEY,
  name            VARCHAR(200) NOT NULL,
  email           VARCHAR(255) UNIQUE,
  phone           VARCHAR(32),
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

**Indexes/notes:** index on email for lookup.

---

### `wallet_account`

Tracks wallet balances (single wallet per customer assumed — adapt for multi-wallet).

```sql
CREATE TABLE wallet_account (
  wallet_id       VARCHAR(36) PRIMARY KEY,
  customer_id     VARCHAR(36) NOT NULL REFERENCES customer(customer_id),
  balance         NUMERIC(18,2) NOT NULL DEFAULT 0.00,
  currency        VARCHAR(3) NOT NULL,     -- e.g. INR, USD
  status          VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_wallet_customer ON wallet_account(customer_id);
```

**Notes:** Use DB-level checks / application locks for concurrent balance updates (SELECT FOR UPDATE or optimistic locking via version column).

---

### `wallet_transaction_request`

Temporary/persistent record of initiation requests (before Payment service settles).

```sql
CREATE TABLE wallet_transaction_request (
  request_id      VARCHAR(36) PRIMARY KEY,
  customer_id     VARCHAR(36) NOT NULL REFERENCES customer(customer_id),
  wallet_id       VARCHAR(36) NOT NULL REFERENCES wallet_account(wallet_id),
  merchant_id     VARCHAR(36) NOT NULL,
  product_name    VARCHAR(255),
  product_cost    NUMERIC(18,2) NOT NULL,
  currency        VARCHAR(3) NOT NULL,
  status          VARCHAR(32) NOT NULL DEFAULT 'PENDING', -- PENDING,SENT_TO_PAYMENT,SUCCESS,FAILED
  payment_txn_id  VARCHAR(36), -- filled when Payment Service returns txn id
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_req_customer ON wallet_transaction_request(customer_id);
CREATE INDEX idx_req_status ON wallet_transaction_request(status);
```

**Notes:** Keep this as source-of-truth for UI; Payment service writes back payment_txn_id and final status.

# 2) Payment Service — tables & DDL

### `payment_transaction`

Core transaction table for payment lifecycle.

```sql
CREATE TABLE payment_transaction (
  transaction_id  VARCHAR(36) PRIMARY KEY,
  request_id      VARCHAR(36), -- FK to wallet_transaction_request.request_id (kept as reference)
  wallet_id       VARCHAR(36) NOT NULL,
  customer_id     VARCHAR(36) NOT NULL,
  merchant_id     VARCHAR(36) NOT NULL,
  amount          NUMERIC(18,2) NOT NULL,   -- original amount
  fee             NUMERIC(18,2) NOT NULL DEFAULT 0.00,
  net_amount      NUMERIC(18,2) NOT NULL,   -- amount credited to merchant
  status          VARCHAR(32) NOT NULL,     -- INITIATED, SUCCESS, FAILED, REVERSED
  failure_reason  TEXT,
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now(),
  updated_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_payment_request ON payment_transaction(request_id);
CREATE INDEX idx_payment_status ON payment_transaction(status);
CREATE INDEX idx_payment_wallet ON payment_transaction(wallet_id);
```

**Notes:** `transaction_id` should be generated as a UUID. `fee` business rule applied here.

---

### `transaction_ledger`

Immutable ledger entries (debits and credits).

```sql
CREATE TABLE transaction_ledger (
  ledger_id       VARCHAR(36) PRIMARY KEY,
  transaction_id  VARCHAR(36) NOT NULL REFERENCES payment_transaction(transaction_id),
  entry_type      VARCHAR(16) NOT NULL, -- DEBIT_WALLET / CREDIT_MERCHANT / FEE
  account_id      VARCHAR(36) NOT NULL, -- wallet_id or merchant_id depending on entry_type
  amount          NUMERIC(18,2) NOT NULL,
  currency        VARCHAR(3) NOT NULL,
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_ledger_txn ON transaction_ledger(transaction_id);
CREATE INDEX idx_ledger_account ON transaction_ledger(account_id);
```

**Notes:** Ledger must be append-only; don't update rows — create reversal entries for reversals.

---

### `wallet_balance_snapshot`

Snapshots before/after a wallet debit for audit and reconciliation.

```sql
CREATE TABLE wallet_balance_snapshot (
  id              BIGSERIAL PRIMARY KEY,
  transaction_id  VARCHAR(36) NOT NULL REFERENCES payment_transaction(transaction_id),
  wallet_id       VARCHAR(36) NOT NULL,
  old_balance     NUMERIC(18,2) NOT NULL,
  new_balance     NUMERIC(18,2) NOT NULL,
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_snapshot_wallet ON wallet_balance_snapshot(wallet_id);
```

---

### `audit_log`

General audit trail for payment steps.

```sql
CREATE TABLE audit_log (
  audit_id        BIGSERIAL PRIMARY KEY,

  event_type      VARCHAR(64) NOT NULL,

  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now()

CREATE INDEX idx_audit_txn ON audit_log(transaction_id);
```

**Notes:** store details as JSONB for flexible structured data.

### `compensation_queue`

For retries/compensating actions (e.g., if a downstream step failed).

```sql
CREATE TABLE compensation_queue (
  id              BIGSERIAL PRIMARY KEY,

  failed_step     VARCHAR(64) NOT NULL,

  retry_count     INT NOT NULL DEFAULT 0,
  status          VARCHAR(16) NOT NULL DEFAULT 'PENDING', -- PENDING, IN_PROGRESS, FAILED, DONE
  last_attempt_at TIMESTAMP WITH TIME ZONE,
  created_at      TIMESTAMP WITH TIME ZONE DEFAULT now()
);

CREATE INDEX idx_comp_txn ON compensation_queue(transaction_id);
```

# Extra cross-service considerations (practical notes)

* **Idempotency:** enforce uniqueness on `payment_transaction.request_id` or `merchant_credit_log.transaction_id`. Use idempotency keys on APIs.
* **Concurrency:** update balances using DB transactions + `SELECT ... FOR UPDATE` or optimistic locking (version column).
* **Audit & retention:** keep immutable ledger/ audit_log for reconciliation; consider partitioning older data (time-based) or moving to archive store.
* **Scaling:** put hot tables behind read replicas (e.g., `wallet_account` reads) and use horizontal partitioning for ledger/audit tables.
* **Timezones/dates:** store timestamps in UTC (`TIMESTAMP WITH TIME ZONE`) for consistency.
* **Data types:** `NUMERIC(18,2)` for amounts; adjust precision for currencies needing more precision.
* **Foreign keys:** for cross-service references (e.g., payment_transaction.request_id) you may or may not enforce FK constraints across microservice DBs — many teams prefer keeping each service DB autonomous and relying on `request_id` as a reference without enforced FK.
* **Compensation/Retry:** `compensation_queue` and `notification_retry_log` help with eventual consistency.
